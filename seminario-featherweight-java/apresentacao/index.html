Capítulo 19: tratar como primitivo

Classes e objetos são construções da própria linguagem, com regras de tipo e de avaliação próprias.

É o caminho do Featherweight Java (FJ), proposto por Igarashi, Pierce e Wadler em 1999.

FJ é um subconjunto estrito de Java: todo programa FJ é um programa Java executável, com o mesmo comportamento.
Motivação

Completude contra compacidade

Um modelo formal serve para descrever uma linguagem com precisão e provar propriedades dela, como segurança de tipos.

Quanto mais recursos o modelo cobre, mais pesada fica a prova. FJ escolhe o outro extremo: corta tudo que alonga a prova sem mudar o argumento.

O resultado é útil para estender Java no papel: genéricos (GJ), raw types, classes internas e compilação que preserva tipos foram estudados sobre FJ.

Inside every large language is a small language struggling to get out. Igarashi, Pierce e Wadler (1999)
Recorte

O que FJ mantém de Java e o que corta

Mantém

  • Classes mutuamente recursivas
  • Criação de objetos e acesso a campos
  • Chamada e sobrescrita de métodos
  • Recursão aberta via this
  • Subtipagem e cast

Corta

  • Atribuição: campos só são definidos no construtor
  • Interfaces, sobrecarga, super.m(), null
  • Tipos base (int, bool), exceções
  • Classes internas, métodos abstratos, public/private
  • Concorrência e reflexão

Sem atribuição, FJ é um fragmento funcional de Java. Mesmo assim é Turing-completo: dá para codificar o lambda-cálculo nele.

Exemplo do livro

Um programa é uma tabela de classes mais um termo

class A extends Object { A() { super(); } }
class B extends Object { B() { super(); } }

class Pair extends Object {
  Object fst;
  Object snd;
  // construtor
  Pair(Object fst, Object snd) {
    super(); this.fst=fst; this.snd=snd; }
  // método
  Pair setfst(Object newfst) {
    return new Pair(newfst, this.snd); }
}

Convenções rígidas, para a sintaxe ficar regular:

  • extends sempre escrito, mesmo para Object
  • Construtor sempre presente: um parâmetro por campo, super(...) e depois this.f=f
  • Receptor sempre explícito: this.snd, nunca snd
  • Corpo de método é só return t;

super e = só aparecem dentro do construtor.

Sintaxe

A linguagem inteira tem cinco formas de termo

FormaGramáticaNo exemplo
Variávelxnewfst, this
Acesso a campot.fthis.snd
Chamada de métodot.m(t)new Pair(...).setfst(new B())
Criação de objetonew C(t)new A(), new Pair(..., ...)
Cast(C) t(Pair) t.fst

A barra em t indica sequência: t1, ..., tn.

this é tratado como variável, não palavra-chave. Ele fica implicitamente ligado em todo corpo de método.

Figura 19-1

A gramática completa

CL ::= class C extends C {C f; K M} K  ::= C(C f) {super(f); this.f=f;} M  ::= C m(C x) {return t;} t  ::= x | t.f | t.m(t) | new C(t) | (C) t v  ::= new C(v)

Valores são só objetos com todos os argumentos já avaliados. "Tudo é objeto", como no lambda-cálculo "tudo é função".

Um programa é o par (CT, t): uma tabela de classes e o termo a avaliar, que faz o papel do main.

Metavariáveis: A..E classes, f e g campos, m métodos, x parâmetros, s e t termos, u e v valores.

Seção 19.3

Em Java, o nome do tipo importa

Estrutural

NatPair = {fst:Nat, snd:Nat}

O nome é só abreviação. Subtipagem é decidida comparando a forma dos tipos.

Mais elegante para provas e para recursos avançados (polimorfismo, tipos abstratos). Domina a literatura.

Nominal

class Pair extends Object { ... }

Todo tipo tem nome, e subtipagem é a que o programador declarou com extends.

  • O nome vira etiqueta em tempo de execução: permite cast e instanceof
  • Tipos recursivos saem de graça
  • Checar C <: D é quase trivial

A tabela de classes CT mapeia cada nome de classe para sua declaração.

Object é especial: não está na tabela, não tem campos nem métodos.

Condições de sanidade da tabela:

  • toda classe citada existe em CT
  • Object não está em CT
  • não há ciclo em <:

Três regras fazem todo o trabalho

A figura original divide a avaliação em dois grupos:

  • 3 regras de computação: campo, método e cast. Elas mudam o programa.
  • 5 regras de congruência: escolhem qual subtermo deve avançar primeiro.
E-ProjNew: seleciona o valor de um campo.
E-InvkNew: substitui parâmetros e this.
E-CastNew: elimina um cast válido.

E-Cast

Estratégia chamada por valor: primeiro o receptor, depois os argumentos da esquerda para a direita.

A mesma ideia em forma de contexto de avaliação, um termo com um buraco [] onde está o próximo passo:

E ::= []  |  E.f  |  E.m(t)  |  v.m(v, E, t)
   |  new C(v, E, t)  |  (C)E
Passo a passo

Avaliando um termo com cast, um redex por vez

Termo o redex está sublinhado
((Pair) new Pair(new Pair(new A(),new B()), new A()).fst).snd⟶ ((Pair)new Pair(new A(),new B())).snd⟶ new Pair(new A(),new B()).snd⟶ new B()
Regra aplicada
E-ProjNewdentro de E-Cast e E-Field
Contexto ((Pair)[]).snd. O primeiro campo de Pair é fst, então sai o primeiro argumento: new Pair(new A(),new B()).
E-CastNewdentro de E-Field
O objeto é Pair e Pair <: Pair. O cast passa e desaparece.
E-ProjNew
snd é o segundo campo de Pair: sai o segundo argumento.
valor
new B() não tem mais nada para avaliar. É um valor e a avaliação termina.
Tipos estáticos

Sem o cast, o mesmo termo nem tipa

new Pair(new Pair(new A(), new B()),
         new A()).fst.snd

O campo fst foi declarado como Object. Para o verificador de tipos, ...fst tem tipo Object.

fields(Object) é vazio, então .snd é rejeitado, mesmo que em tempo de execução ali exista um Pair.

((Pair) new Pair(new Pair(new A(), new B()),
                 new A()).fst).snd

O cast abaixa o tipo estático de Object para Pair (downcast). Agora .snd tipa.

O preço: o cast é conferido em tempo de execução e pode falhar. Aqui ele passa, como vimos no passo a passo.

E-InvkNew

Chamar um método é substituir parâmetros e this

Termo
new Pair(new A(), new B()).setfst(new B()) corpo: new Pair(newfst, this.snd)⟶ new Pair(new B(), new Pair(new A(), new B()).snd)⟶ new Pair(new B(), new B())
O que acontece
receptor e argumento já são valores
Nenhuma regra de congruência se aplica. Hora da regra de computação.
mbody(setfst, Pair)
A classe do receptor é Pair. Lá o método tem parâmetro newfst e o corpo ao lado.
[newfst ↦ new B(), this ↦ receptor]
O parâmetro vira o argumento e this vira o próprio receptor. Essa é a recursão aberta via this.
E-ProjNew dentro de E-New-Arg
O acesso .snd restante é avaliado e o resultado é um valor.
Erros em tempo de execução

Três jeitos de uma computação travar

campo inexistente

Acessar campo que a classe não declara

nenhuma regra casa com new A().fst

método inexistente

"Message not understood"

nenhuma regra casa com new A().setfst(...)

cast inválido

Cast para algo que não é superclasse

(A)new B(): B <: A é falso, então E-CastNew não se aplica

FJ não tem exceções: travar é o erro. O sistema de tipos garante que os dois primeiros nunca acontecem. O terceiro só pode acontecer se houver downcast.

Uma regra de tipo para cada forma de termo

x:C ∈ Γ

Γ ⊢ t0 : C0    fields(C0) = C f
Γ ⊢ t0.fi : Ci

Γ ⊢ t0 : C0   mtype(m, C0) = D→C   Γ ⊢ t : C   C <: D
Γ ⊢ t0.m(t) : C

Lê-se Γ ⊢ t : C como "no ambiente Γ, o termo t tem tipo C". Γ guarda o tipo de cada variável.

Não há regra de subsunção solta: o <: aparece só onde é preciso, nos argumentos. A apresentação é algorítmica, como em Java: cada termo tem um tipo mínimo único.

stupid cast

O compilador Java rejeita cast entre classes não relacionadas. Por que FJ aceita?

Porque um termo bem tipado pode virar um assim durante a avaliação:

(A)(Object)new B()   // T-DCast: ok
⟶ (A)new B()          // só T-SCast tipa

Sem T-SCast, a preservação de tipos seria falsa. Uma tipagem FJ só corresponde a uma tipagem Java se não usar essa regra.

  • Método: o corpo é tipado com os parâmetros e com this : C. O resultado pode ser subtipo do declarado.
  • Sobrescrita exige o mesmo tipo da superclasse.
  • Classe: o construtor tem que passar os campos herdados para super e inicializar os próprios.
  • Sem circularidade: os tipos dos métodos são declarados, então a ordem não importa.
Seção 19.5

Bem tipado não trava, exceto em downcast

Preservação

Se Γ ⊢ t : C e t ⟶ t', então Γ ⊢ t' : C' para algum C' <: C.

O tipo pode ficar mais específico durante a avaliação, nunca diferente.

Exemplo: (Object)new A() tem tipo Object e avança para new A(), de tipo A.

Progresso

Se t é fechado, bem tipado e não avança, então t é um valor ou t = E[(C)(new D(v))] com D ≮: C.

A única forma de travar é um downcast que falha. Campo e método inexistentes nunca acontecem.

Se o programa só tem upcasts, ele nunca trava. Em Java completo, o cast que falha vira exceção.

Exercícios do livro

Três perguntas que ajudam a fixar o modelo

Exerc.PerguntaIdeia da resposta
19.4.1Por que não há regra dizendo que Object é supertipo de tudo, como S-Top?Toda classe declara uma superclasse e não há ciclos, então toda cadeia de extends termina em Object. A transitividade já dá C <: Object, e os únicos tipos são classes.
19.4.3Como adicionar atribuição a campos?Seguir o capítulo 13: introduzir locações e uma memória (heap). Objetos passam a ser referências, e a avaliação deixa de acontecer só na sintaxe.
19.4.7Como adicionar super.m()?A busca do corpo precisa começar na superclasse da classe onde o método foi escrito, não na do receptor. O corpo tem que lembrar a classe que o definiu.
Seção 19.6

As duas visões se complementam

Codificação (cap. 18)

  • Expõe os mecanismos de encapsulamento e reuso
  • Mostra como um compilador traduz objetos para algo mais baixo nível

Primitivo (cap. 19)

  • Fala de tipos e avaliação de objetos diretamente
  • Melhor ferramenta para projetar e documentar uma linguagem
O ideal tem as duas: uma linguagem de alto nível com regras próprias, uma tradução para registros e funções, e uma prova de que a tradução preserva tipos e avaliação. Para FJ isso foi feito por League, Trifonov e Shao (2001).
